# 実装上の決定事項（Decisions）

要件定義書（`docs/requirements.md`）に書かれていない／解釈が分かれる点について、実装方針をここで決める。
**要件定義書と矛盾したら要件定義書が優先**。ここを変更するときは、変更理由と日付を追記する。
「状態：提案」の項目は、実装前にユーザー（運営担当）に確認してから「確定」にする。

## D-01 技術スタック（状態：確定）

要件では「フレームワークは実装時に決める」とされているため、以下に決める。

| 用途 | 採用 | 理由 |
| --- | --- | --- |
| ビルド | Vite | 設定が少なく Firebase Hosting にそのまま載る |
| UI | React + TypeScript | 状態の多い会計画面を型で守る |
| ルーティング | react-router | 4画面を独立URLにするため |
| Firebase | Firebase JS SDK（modular API） | Auth / Firestore / Hosting |
| CSVまとめ | JSZip | 複数CSVを1回のダウンロードにする（D-13） |

| E2E（任意） | Playwright | オフライン（`context.setOffline(true)`）での会計を検証 |
| スタイル | 素のCSS（`src/styles.css`）＋ Tailwind CSS v4（2026-10-30 追加：D-31） | 当初は依存を増やさないため素のCSS。今後は Tailwind に移していく |

## D-03 ID の発行（状態：確定）

- `transaction_id`：`crypto.randomUUID()`。「会計確定」を押した瞬間に1回だけ発行し、確定ボタンは直後に無効化する（連打で2件できないように）。
- `device_id`：初回起動時に `dev_` + 英数4桁を生成し、`localStorage` に保存。以後固定。
- `register_id`：端末ごとに設定画面で選ぶ（`reg_1`〜`reg_9`）。`localStorage` に保存。既定は `reg_1`。
- `vr_visits` / `action_logs` / `register_closings` のIDも端末側で UUID を発行し、ドキュメントIDにする。

## D-04 Firestore のドキュメント形（状態：確定）

フィールド名は CSV の列名と同じ snake_case にそろえ、エクスポート時の変換を最小にする。

```ts
// transactions/{transaction_id}
{
  schema_version: 1,
  transaction_id: string,
  timestamp: string,          // 端末時刻の ISO 8601（例 2026-11-03T14:05:22+09:00）
  created_at: Timestamp,      // serverTimestamp()。監査用。CSVには出さない
  group_type: 'family' | 'student' | 'adult' | 'other' | 'unknown',
  group_size: 1 | 2 | 3 | 4 | 5,   // 5 = 5人以上
  lines: Array<{
    line_no: number, item: 'design_1' | 'design_2' | 'design_3' | 'set',
    quantity: number, unit_price: number, amount: number,
    design_1_qty: number, design_2_qty: number, design_3_qty: number,
  }>,
  total: number, received: number, change: number,
  design_1_qty: number, design_2_qty: number, design_3_qty: number,  // 明細の合計
  register_id: string, device_id: string,
  is_void: boolean, voided_at: string | null,
  is_test: boolean,
}
```

- 明細は「商品ごとに1行」。案1を2枚なら `quantity: 2` の1行。
- セット1個は `design_1_qty = design_2_qty = design_3_qty = 1`（個数分）。

## D-05 取消（状態：確定）

- 取消は `is_void: true` と `voided_at` の2フィールドだけを更新する。他のフィールドは変更不可（ルールで強制）。取消の取り消し（復活）はしない。間違えたら入れ直す。
- 「直前の取消」＝この端末で確定した、まだ取り消していない最新の会計。ワンタップで実行し、何を取り消したかをトーストで表示する。
- 過去の会計は一覧から選んで取り消す（こちらは確認ダイアログあり）。

## D-06 テストモード（状態：確定）

- `settings/current.test_mode` に持ち、全端末で共有する（開店前の確認を1か所で済ませるため）。
- 会計確定時点の値を各ドキュメントの `is_test` に焼き込む。
- テストモード中は全画面（お客さん用画面を除く）の上部に、色付きの帯を常時表示する。
- 懸念：オフライン中の端末には切替が届かない。開店前チェックで全端末の帯が消えたことを目視確認する運用にする。
- 切替の記録・確認ダイアログ・お客さん用画面の表示は D-24 を参照。

## D-08 預かり金とお釣り（状態：確定）

- 金額ボタン（500／1000／5000／10000）は押すたびに加算。「ちょうど」は預かり金を合計額に置き換える。「預かりクリア」で0に戻す。
- 「会計確定」が押せる条件：カートが空でない／客層を選択済み／人数を選択済み／預かり金 ≥ 合計。
- 押せないときは、何が足りないかをボタンの近くに表示する。

## D-09 確定後の画面（状態：確定）

- 確定後はお釣りを画面中央に大きく表示し、次に商品ボタンを押した時点で新しい会計を始める。
- お客さん用画面は確定内容（お釣り）を約10秒表示してから、待機表示（商品と価格の案内）に戻る。

## D-10 お客さん用画面の同期（状態：確定）

- 同じブラウザ：`BroadcastChannel('pos-display:' + register_id)` で即時送信（オフラインでも動く）。
- 別端末：`display_state/{register_id}` を上書き保存（これは表示用の状態であり会計データではないので上書き可）。送信は300ms程度に間引く。
- お客さん用画面は両方を購読し、`updated_at_ms`（送信元端末の時刻）が新しい方を表示する。
- 表示データの形：`{ register_id, mode: 'idle' | 'cart' | 'done', lines, total, received, change, updated_at_ms }`。
- お客さん用画面が落ちてもスタッフ入力画面は影響を受けないこと（送信失敗は握りつぶしてログだけ出す）。

## D-11 通信状態と未送信件数（状態：確定）

- 通信状態：`navigator.onLine` と、Firestore スナップショットの `metadata.fromCache` を合わせて「オンライン／オフライン」を表示。
- 未送信件数：`onSnapshot(..., { includeMetadataChanges: true })` で、`metadata.hasPendingWrites` が true のドキュメント数を数える。
- **注意**：オフライン中は `setDoc()` の Promise がサーバー到達まで解決しない。会計確定で `await` して画面を止めないこと（書き込みは投げっぱなしにし、エラーだけ拾う）。
- データ量は最大でも会計数百件なので、コレクション全体を購読してよい（Sparkプランの読み取り枠に十分収まる）。

## D-12 時刻（状態：確定）

- `timestamp` は端末のローカル時刻を、端末のタイムゾーンオフセット付き ISO 8601 で出す（`+09:00`）。`toISOString()`（UTC・`Z`表記）は使わない。
- 端末時計がずれていると分析が狂うので、開店前チェックに「端末の時刻確認」を入れる。

## D-13 CSV の細かい書式（状態：確定）

- **BOMなしUTF-8**（BOMがあると pandas の既定読み込みで先頭列名に `\ufeff` が付き、「前処理なし」が崩れる）。
- 改行は `\n`。真偽値は `true` / `false`（小文字）。数値は整数のまま。
- 値にカンマ・改行・ダブルクォートを含む場合だけ `"` で囲み、`"` は `""` にする（主に施策ログのメモ）。
- 並び順：`timestamp` 昇順、同時刻は `transaction_id`、明細は `line_no` 昇順。
- ダウンロードは ZIP 1つにまとめる：`pos_export_{register_id}_YYYYMMDD_HHmmss.zip`（例 `pos_export_reg_1_20261103_143005.zip`。時刻は端末ローカル）。中身のファイル名は要件どおり `sales_lines.csv` などで固定（分析スクリプトを変えずに済む）。
  - 2026-10-20 変更：旧 `pos_export_YYYYMMDD_HHmm.zip`。保存先を共有フォルダ1か所にまとめる（D-23）ため、レジ番号と秒を入れて名前がぶつからないようにした。
- Excel で開いたときの文字化けは許容する（分析の主対象は pandas / Tableau のため）。

## D-14 要件で列が定義されていないCSV（状態：確定）

| ファイル | 列 |
| --- | --- |
| transactions.csv | transaction_id, timestamp, group_type, group_size, total, received, change, design_1_qty, design_2_qty, design_3_qty, total_sheets, set_qty, register_id, device_id, is_void, is_test（total_sheets・set_qty は 2026-10-20 に追加） |
| vr_visits.csv | visit_id, timestamp, register_id, device_id, is_void, is_test |
| action_logs.csv | log_id, timestamp, log_type, note, register_id, device_id, is_test（log_type は 2026-10-20 に追加。値は manual / test_mode_on / test_mode_off / csv_export / set_limit_change：D-24, D-25, D-30） |
| register_closings.csv | closing_id, timestamp, business_date, register_id, device_id, system_cash_sales, counted_cash, float_amount, difference, is_test |

- transactions.csv の列順は要件 6.2 末尾の記述どおり（`total_sheets`・`set_qty` は「絵柄別枚数の合計」の直後に追加）。
- transactions.csv の追加列（2026-10-20 確定）：
  - `total_sheets`（整数）：その会計で出ていった合計枚数＝`design_1_qty + design_2_qty + design_3_qty`。
  - `set_qty`（整数）：その会計のセットの個数＝明細のうち `item = set` の `quantity` の合計（セットが無ければ 0）。
  - どちらも Firestore には保存せず、CSV 出力時に会計ドキュメントから計算する。取消・テストの会計にも同じように値を入れる。
  - `scripts/check_csv.py` で、`total_sheets` が3列の合計と、`set_qty` が `sales_lines.csv` のセット明細の会計ごとの合計と一致することを検査する。
- **`local_datetime` 列（2026-10-21 追加。5つのCSVすべて）**：
  - `timestamp` 列を持つ5つのCSV（sales_lines / transactions / vr_visits / action_logs / register_closings）すべてで、`timestamp` の**直後**に `local_datetime` を置く。上の表の列順は、それぞれ `timestamp` の後ろに `local_datetime` が入ったものと読み替える。
  - 形式：`2026-11-03 14:05:22`（日本時間、秒まで、タイムゾーン表記なし）。
  - 値は `timestamp` と同じ時刻を**日本時間（Asia/Tokyo）**で表したもの。端末のタイムゾーン設定に左右されないよう、`timestamp` を絶対時刻に直してから UTC+9 に変換する（日本時間はサマータイムが無いので +9 時間固定）。Firestore には保存せず、CSV 出力時に計算する。
  - `timestamp` 列は変更せずに残す。
  - 理由：Tableau はオフセット付き ISO 8601（`2026-11-03T14:05:22+09:00`）を日時と自動認識せず、文字列として読み込むため（2026-10-21 にユーザーが確認）。
  - **使い分け**：Tableau では `local_datetime`（日時として自動認識される）、pandas では `timestamp`（`pd.to_datetime` でタイムゾーン付きの日時になる。`local_datetime` は既定では文字列として読まれる）。
  - sales_lines.csv は要件 6.2 で列が決まっているが、この列の追加はユーザーの指示による（要件定義書そのものは書き換えない）。
  - `scripts/check_csv.py` で、`local_datetime` が形式どおりか、`timestamp` を日本時間にした値と一致するかを検査する。
- **`cashier_id` 列（2026-10-23 追加。D-27）**：
  - sales_lines.csv・transactions.csv・register_closings.csv の3つで、`device_id` の**直後**に `cashier_id` を置く。上の表の列順は、それぞれ `device_id` の後ろに `cashier_id` が入ったものと読み替える。vr_visits.csv・action_logs.csv には入れない。
  - 値は `cs_` + 英小文字・数字4桁（例 `cs_k3f9`）。この機能より前の記録は `unknown`。空欄は作らない。
  - 担当者の**名前はどのCSVにも出さない**（個人情報を分析データに入れないため）。
  - sales_lines.csv は要件 6.2 で列が決まっているが、この列の追加はユーザーの指示による（要件定義書そのものは書き換えない）。
  - `scripts/check_csv.py` で、値が `cs_xxxx` か `unknown` であること（名前が紛れ込んでいないか）と、同じ会計の `cashier_id` が transactions.csv と sales_lines.csv で一致することを検査する。
- レジ締め（F-13）の保存先は要件 6.4 に無いため、コレクション `register_closings` を追加する。
- `counted_cash` は「数えた現金の総額」、`difference = (counted_cash − float_amount) − system_cash_sales`。

## D-15 在庫計算（状態：確定）

- `残数[案n] = initial_stock[案n] − Σ design_n_qty`（`is_void = false` かつ `is_test = false` の会計のみ）。
- 商品ボタンの無効化は「カートに入っている分」も差し引いて判定する。セットは3絵柄すべてに1枚以上の余りが必要。
- 残数 ≤ `low_stock_threshold` の絵柄は強調表示（色＋「残りわずか」）。

## D-16 ログインとセキュリティルール（状態：確定）

- 部員共通アカウントは Firebase コンソールで1つだけ作る。アプリに新規登録画面は作らない。
- **Firebase Authentication はクライアントから誰でもアカウント作成できてしまう**ため、次の二重の対策をとる：
  1. コンソールで新規登録（sign-up）を無効化する（Authentication → 設定 → ユーザーアクション）。
  2. ルール側でも共通アカウントのメールアドレスと一致することを確認する。
- ルールの要点：
  - `transactions` / `vr_visits`：作成は共通アカウントのみ。更新は `is_void` と `voided_at` だけ。削除禁止。
  - `action_logs` / `register_closings`：作成のみ。更新・削除禁止。
  - `settings`：共通アカウントのみ読み書き。
  - `display_state`：**読み取りは誰でも可**（お客さん用画面はログイン不要）。書き込みは共通アカウントのみ。
- ログイン状態はブラウザに保存されるので（既定の永続化）、一度ログインすればオフライン中も使える。

## D-17 日別の区切り（状態：未決 → 要件 8.2 待ち）

日程と営業時間が決まるまでは、`timestamp` のローカル日付で区切る。ダッシュボードには日付の切替を付ける。CSVに日付列は追加しない（`timestamp` から導出できるため）。

## D-18 割引（状態：未決 → 要件 8.2 待ち）

当面は「設定画面で価格を変える」ことで対応する（販売時点の単価が明細に残るので分析は崩れない）。割引ボタンなどが必要になったら、`item` の種類を増やす前に要件を相談する。

## D-20 セキュリティルールの「再送」の扱い（状態：確定）

オフライン復帰時に SDK が同じ書き込みを再送すると、2回目はルール上「更新」として評価される。
このとき `created_at`（serverTimestamp）だけが変わるため、更新で `created_at` が変わることは許可する。
会計・VR体験の内容（金額・明細など）の変更、取消の取り消し、削除は引き続き禁止。

- `transaction_id` などの UUID は `crypto.randomUUID()` を使い、http（LAN の IP 直打ち）などで使えない場合だけ `crypto.getRandomValues()` による UUID v4 で代替する（`src/lib/uuid.ts`）。`Math.random` は使わない（2026-10-20 に確認済み。`device_id` の生成も `crypto.getRandomValues()`）。

## D-23 エクスポートしたCSVの保存先（状態：確定 2026-10-20 変更）

**決定**
- 保存先は、DA研アカウントの Google ドライブ「マイドライブ\2026_経営陣\07_商大祭\99_POSデータ保存場所」の1か所に統一する。
- エクスポートは「エクスポート担当」の端末1台で行う（30分ごとと各日の閉店時）。エクスポートするのは「オンライン」かつ「未送信 0件」のときに限る。
- アプリはこれまでどおりブラウザの通常のダウンロードとして ZIP を保存するだけ。担当PCは「パソコン版 Google ドライブ」の同期フォルダを Chrome のダウンロード先にし、PCが使えないときはタブレット・スマホから手動でアップロードする（手順は `docs/operations.md`）。
- ZIP のファイル名にレジ番号と秒を入れる（D-13）。

**要件定義書 8.2 からの変更と理由**
- 要件 8.2 の未決事項「エクスポートしたCSVの保存先」は、原本で「それぞれのアクセスしている端末で決定」とされていたが、2026-10-20 にユーザー（運営）の判断で上記の1か所に変更した（要件定義書そのものは書き換えない）。
- 理由：
  - 端末ごとに保存先が違うと、分析のときにどれが最新・完全なデータか分からなくなる。1か所にまとまっていれば、分析担当は最新の ZIP を1つ取るだけで済む（要件 8.1「共有ドライブに保存する」にも沿う）。
  - ZIP には、エクスポートした端末に届いている**全レジ分**の記録が入るため、全端末が出す必要はない。1台に絞れば同じ内容のファイルが重複しない。
  - オンラインかつ未送信 0件のときに限るのは、オフライン中の端末から出すと他端末の未送信分が含まれず、不完全な ZIP が共有フォルダに混ざるため。
- 旧決定：アプリは ZIP をダウンロードするだけにし、保存先は各端末の運用で決める。

## D-24 テストモード切替の記録（状態：確定 2026-10-20）

D-06 の補足。いつからいつまでがテスト（練習）だったかを後から確かめられるようにする。

**記録の内容**
- テストモードを切り替えると、施策ログ（`action_logs`）に自動で1件記録する。`note` は「テストモードをオンにした」／「テストモードをオフにした」。
- 時刻・端末ID・レジ番号は手入力の施策ログと同じように入れる。
- この自動記録は、テストモード中かどうかにかかわらず**常に `is_test=false`**（本番とテストの境目を示す記録なので、分析時に除外されないようにする）。
- 施策ログに種類の列 `log_type` を追加する。値は `manual`（手入力）／`test_mode_on`／`test_mode_off`（のちに D-25 で `csv_export` を追加）。`action_logs.csv` にも `timestamp` の次の列として出力する（D-14 を更新）。
- `log_type` が無い追加前の記録は、読み込み時に `manual` として扱う。

**片方だけ成功しないようにする**
- 切替（`settings/current.test_mode`）と記録（`action_logs/{log_id}`）は、Firestore の `writeBatch` で1回の書き込みにまとめる。バッチは端末内でもサーバーでも「全部反映」か「全部失敗」のどちらかになる。
- オフライン中に切り替えても、切替と記録は一緒に端末に保存され、復帰後に1回の送信で一緒に届く。
- `settings/current.test_mode_log_id` に、その切替の記録の ID を入れる。
- セキュリティルールでも次を強制する（`getAfter` で同じ書き込みの中身を確認する）：
  - `test_mode` を変える書き込みは、同じ書き込みで**新しく作られる**、向きの合った記録（`test_mode_on`／`test_mode_off`）を指している場合だけ通す。既存の記録の使い回しは不可。
  - `test_mode_on`／`test_mode_off` の記録は、同じ書き込みで settings がその記録を指し、向きが合っている場合だけ作れる。`is_test=true` にはできない。
  - `log_type` が無い・不明な値の施策ログは作れない。
  - `settings` の削除は不可。
- 切替の前には、オン・オフとも確認ダイアログを出す（実装済み）。

**お客さん用画面の「TEST」表示は現状のままとする**
- スタッフ画面（レジ・ダッシュボード・設定）には、目立つ帯を常時表示する。
- お客さん用画面は来場者向けなので大きなバナーは出さず、左上に小さく「TEST」と出す現状のままとする（D-06 の「お客さん用画面を除く」に沿う）。
- 既知の制約：この「TEST」はレジ画面が送る表示データで切り替わるため、そのレジ番号のレジ画面が開いていないと、開くまで反映されない。オフラインの別端末にも届かない。開店前チェック（`docs/operations.md`）の目視確認で補う。

## D-25 CSVエクスポートの記録（状態：確定 2026-10-20）

D-22（バックアップ通知を全端末共通にする）と D-23（エクスポート担当1台）のための決定。

- CSV をエクスポートすると、施策ログ（`action_logs`）に `log_type = csv_export` の記録を自動で1件残す。`note` は「CSVをエクスポートした（{ZIPのファイル名}）」。時刻・端末ID・レジ番号は他の施策ログと同じ。
- この記録は**常に `is_test=false`**（テストモード中でも、バックアップを取った事実は本番の運用記録なので）。
- テストモード切替（D-24）と違って settings と組で書く必要はないので、単独の書き込み。オフライン中も端末に保存され、復帰後に自動で送信される（他の書き込みと同じ）。
- 記録はダウンロードの**後**に作るので、その ZIP 自身には含まれない（次の ZIP から入る）。
- 状態バーの「CSV保存」と設定画面の「最後のエクスポート」は、全端末の `csv_export` 記録のうち最新の `timestamp` からの経過時間で出す（D-22）。他端末の時計が進んでいて経過時間が負になる場合は 0 分とする。
- `action_logs.csv` の `log_type` に値 `csv_export` が加わる（列は変えない。D-14）。`scripts/check_csv.py` もこの値を正しいコードとして扱い、`is_test=false` であることを検査する。
- セキュリティルール：`csv_export` の記録は `is_test == false` のときだけ作れる。更新（再送を除く）・削除は他の施策ログと同じく不可。
- 設定画面では、オフライン中または未送信があるときにエクスポートの注意を出す（エクスポート自体は止めない。会計を止めない原則と、バックアップを取れなくなるよりはよいため）。
- 設定画面の施策ログ一覧（最新10件）には `csv_export` を**出さない**。30分ごとに増えるため、手入力のメモが一覧から押し出されてしまうのを防ぐ。テストモード切替（`test_mode_on`／`test_mode_off`）は本番とテストの境目の確認に使うので一覧に残す。最後のエクスポートは一覧の代わりに、状態バーと設定画面のエクスポート欄で分かる。`action_logs.csv` には引き続き `csv_export` も含めて出力する（2026-10-20 決定）。

## D-27 レジ担当者の選択（状態：確定 2026-10-23）

ユーザーの要求と、提案への回答（5点とも提案どおり＋追加2点）で決定。

**データ**
- コレクション `cashiers`（担当者1人＝1ドキュメント）：`cashier_id`（＝ドキュメントID。`cs_` + 英小文字・数字4桁を端末で作る）、`name`（1〜20文字）、`active`、`created_at`、`updated_at`。
- 名前は**呼び名・イニシャル**で登録する運用（要件7「個人情報は扱わない」のため）。設定画面に注意書きを出す。名前は Firestore にだけ保存し、CSV にも、お客さん用画面の表示データ（`display_state`）にも入れない。
- 削除はしない。`active=false` で「無効」にし、選択肢から外す。名前の変更はできる（記録は ID なので過去の分析に影響しない）。
- 会計（`transactions`）とレジ締め（`register_closings`）に `cashier_id` を記録する。確定時の担当者を焼き込み、後から担当者を変えても過去の記録は変わらない。明細（`lines`）には持たせない。会計の `schema_version` は 2。
- この機能より前の記録（`cashier_id` なし）は、読み込み時と CSV で `unknown` として扱う。
- VR体験・施策ログには記録しない。

**端末の「いまの担当者」**
- 会計ごとではなく端末ごとに選ぶ（`localStorage` の `pos.cashier`。選んだ日付も一緒に保存）。画面上部の「担当」に常に表示し、交代するときだけ選び直す。
- **日付（日本時間）が変わったら未選択に戻す**（開店時に選び直す流れにするため）。端末のタイムゾーンに左右されないよう日本時間で判定する。
- **無効にされた担当者が選ばれている端末は、未選択と同じ扱い**。
- 未選択のときは会計確定・レジ締めができない（理由を画面に出す）。**テストモード中も必須**（練習も本番と同じ流れにするため）。

**セキュリティルール**
- `cashiers`：共通アカウントだけ読み書き。作成時に ID の形・ドキュメントIDとの一致・名前1〜20文字・`active` が真偽値・決まった項目だけ、を確かめる。更新できるのは `name`・`active`・`updated_at` だけ。削除不可。
- `transactions`・`register_closings`：作成時に `cashier_id` が `cs_xxxx` の形であることを求める（`unknown` や名前は不可）。取消の更新は従来どおり。機能追加前の会計も取消はできる。
- `display_state`：ログインなしで読めるので、決まった項目（`register_id`, `mode`, `lines`, `total`, `received`, `change`, `prices`, `sold_out`, `is_test`, `updated_at_ms`）以外は書けない（担当者の名前・ID を含められない）。ルールのテストで確認する。

**本番に出す順番**
- ルールで `cashier_id` を必須にするため、**アプリの公開 → ルールのデプロイ** の順で行う。逆にすると、古いアプリを開いたままの端末の会計がルールで拒否される。
- ルールをデプロイする前に、全端末で「未送信 0件」を確認する（古いアプリで未送信のまま残った会計は、`cashier_id` が無いため新しいルールで拒否される）。
- デプロイ後は、全端末でページを読み込み直す。

## D-28 オフラインでも開ける画面（Service Worker）と、新しい版への切り替え（状態：確定 2026-10-29。本番に導入する）

**背景**
- これまで Service Worker は無く、画面（HTML・JS）はブラウザの通常のキャッシュ（`max-age=3600`）に頼っていた。オフライン中に再読み込みすると開けず、開き直しも最後の読み込みから1時間以内しか開けなかった（2026-10-28 に Chromium で確認）。
- 「index.html を保存しない」設定だけを入れると、新しい版にはすぐ切り替わるが、オフラインの開き直しもできなくなる。
- 両立のため、vite-plugin-pwa（1.3.0。ビルド時だけ使うプラグイン。中身は Workbox）を追加する（ユーザー了承済み）。

**決定**
- Service Worker で画面一式（HTML・JS・CSS・画像。約1MB）を端末に保存する。どのURL（`/display` など）でも保存済みの `index.html` で起動する。Firebase Hosting の予約URL（`/__/`）は横取りしない。Firestore の通信は Service Worker を通さない（データの扱いは従来どおり）。
- 各端末で一度はオンラインで開く必要がある。HTTPS でのみ動く（本番は可。LAN の http 開発環境では動かない）。
- **新しい版は自動で切り替えない**。開いたときと10分ごとに新しい版を確認し、届いたら状態バーに「新しい版があります［更新］」を出す。切り替えるのは［更新］を押したときか、次に開いたとき。**会計の途中**（カートに商品・預かり金・客層・人数のどれかがある）は［更新］を押せない（「会計のあとで更新」と表示）。
- お客さん用画面・ログイン画面には状態バーが無いので、次に開いたときに新しい版になる。
- `firebase.json`：すべてのURLに `Cache-Control: no-cache`（`index.html`・`sw.js` を毎回サーバーに確認させ、新しい版にすぐ気づけるように）。`/assets/**` はファイル名に版（ハッシュ）が入るので `max-age=31536000, immutable`。
- 設定画面「この端末」に「アプリの版」（ビルドした日時。日本時間）を出す。実機でどの版が動いているか確かめるため。
- **緊急時の版**：`npm run build:no-sw`（Vite の mode=nosw）でビルドして公開すると、端末の Service Worker と保存した画面を消す版になる。不具合で古い版が端末に残り続けるときに使う。手順は `docs/operations.md`「緊急時：画面の保存（Service Worker）を外す」。元に戻すには通常の `npm run build` で公開し直す。
- E2E：本番と同じ形のビルド（`vite build --mode e2e`。Emulator に接続）を `vite preview` で配り、「オフラインで再読み込みしても開ける」「新しい版で［更新］が出る（会計の途中は押せない）」「緊急時の版で外れる」を確かめる（`tests/pwa/`、`playwright.pwa.config.ts`）。`npm run test:e2e` で通常の E2E と続けて実行する。

**判断の基準（本番に入れるかどうか）**
- 本番に入れるのは、ユーザーが実機（PC の Chrome と iPhone / iPad の Safari）で確認してから。
- **リハーサルの時点で実機の確認が取れていなければ、Service Worker は本番に入れず、運用ルール（オフライン中は再読み込みしない・タブを閉じない：`docs/operations.md`「Wi-Fi が切れたとき」）で本番を迎える。**

**結果（2026-10-29）**

## D-29 シールの表示名（状態：確定 2026-10-29）

キャラ名がまだ決まっていないため、画面に出す絵柄の名前（既定は「案1〜3」）を設定画面から後で変えられるようにする（ユーザーの要求）。

- 変えられるのは**画面に出す名前だけ**。CSV のコード値（`item` の `design_1`〜`design_3`、`set`）と列は変えない。セットの名前は「セット」のまま。
- 保存先：`settings/current.item_labels`（`{ design_1, design_2, design_3 }`）。空欄・未設定は「案1〜3」。
- 名前は前後の空白を除いて**12文字まで**（絵文字なども1文字と数える）。3つの名前は重ねられない（未設定の「案N」とも）。「セット」は使えない。重なりのエラーは、入力した側（後の絵柄、または「案N」と重なった側）に出す。
- 反映先：レジ画面（商品ボタン・カート・在庫表示・取消の通知・会計一覧）、お客さん用画面（待機中のカード・セットの説明・会計中の明細）、ダッシュボード（グラフ）、設定画面（価格・在庫の欄の名前）。
- お客さん用画面には、価格と同じく表示データ（`display_state.labels`）で送る（お客さん用画面はログインしないので `settings` を読めないため）。そのためセキュリティルールの `display_state` の「書いてよい項目」に `labels` を足した。名前は個人情報ではない。
- 長い名前は、ボタン・カードの中で折り返して収める（スマホ幅では商品名を少し小さく）。ダッシュボードのグラフの名前の欄は、一番長い名前に合わせて9文字分ほどまで広げ、それを超えたら折り返す。12文字の名前・幅の広い英字12文字で、PC幅とスマホ幅のスクリーンショットと E2E（横にはみ出さないこと）で確認した。
- **本番に出す順番**：お客さん用画面へ送る表示データに `labels` が増えるため、**ルールのデプロイ → アプリの公開** の順にする（D-27 とは逆）。アプリを先に出すと、古いルールが `labels` 付きの表示データを拒否し、別端末のお客さん用画面が更新されない。新しいルールは古いアプリの表示データ（`labels` なし）も受け付けるので、ルールを先に出しても問題ない。

## D-30 セットの販売上限（状態：確定 2026-10-29）

セットの売れ方を調整するため、セットの販売数に全体の上限を設ける（ユーザーの要求）。

**設定**
- 設定画面に「セットの販売上限」を置く。**0〜100 の整数**、初期値は **100**（実質、制限なし）。全端末で共有する。
- 保存先：`settings/current.set_limit`。まだ保存していない本番の settings では 100 として扱う。価格・在庫の「保存」とは別のボタンで変える（下の記録と組で書くため）。
- 保存の前に確認ダイアログを出す（変更前 → 変更後。販売済みより低くするときはその旨も）。

**変更の記録**
- 上限を変えると、施策ログ（`action_logs`）に `log_type = set_limit_change` の記録を自動で1件残す。売れ行きを見て調整した記録を、あとで分析に使うため。
- `note` は「セットの販売上限を変更した（{変更前}→{変更後}）」で形を固定する。分析では正規表現 `（(\d+)→(\d+)）` で変更前・変更後を取り出せる。CSV の列は増やさない（D-14）。
- 常に `is_test=false`（テストモード中に変えても。上限は本番・テスト共通の設定のため）。
- 上限の変更と記録は、テストモード切替（D-24）と同じく `writeBatch` で1回の書き込みにまとめる。`settings/current.set_limit_log_id` にその記録の ID を入れる。
- 「変更前」はその端末から見えていた値。オフラインの2台がほぼ同時に変えた場合、後から届いた記録の「変更前」が実際の直前の値と食い違うことがある（例：A が 100→80、B が 100→90。サーバーの最終値は後に届いた方）。分析では `timestamp` 順に並べ、「変更後」を正として扱う。
- 設定画面の施策ログ一覧には出す（「自動」の印つき。頻繁には増えないため）。

**残りセット数**
- 残りセット数 ＝ 上限 − 販売済みのセット数。販売済みのセット数は、`is_void=false` かつ `is_test=false` の会計の明細で `item = set` の `quantity` の合計（在庫と同じく保存せず毎回計算）。
- テストモード中の扱いは在庫と同じ：テストの会計は数えない（テストモード中に売ったセットで残りは減らない）。
- 販売済みより低い上限に変えた場合、残りは **0**（マイナスにしない）。
- 案1〜3のどれかの在庫が足りないときは、上限に関係なくセットは売れない（従来どおり）。単品は上限に関係なく売れる。

**画面**
- レジ画面：セットのボタンに「残り◯セット」。数は「残りセット数」と「3絵柄の在庫で作れるセット数」の少ない方から、カートに入っているセットの数を引いたもの（他の商品ボタンの「残り」と同じく、カートの分を引いた数）。0 になったら押せない。在庫が原因で押せないときは従来どおり「在庫なし」。カートの ＋ でも、残りを超えて増やせない。
- お客さん用画面（2026-10-29 変更。ユーザーの要求）：待機中のカードの残り数は、案1〜3とセットのどれも、**「残りわずか」の基準（設定画面の値。初期値10）より多いときは出さない**。基準以下になったら、案1〜3は「あと◯枚」、セットは「あと◯セット」とだけ出す（「残りわずか」という文言は出さない。2026-10-30 ユーザーの指示で変更）。0 になったら価格の代わりに「売り切れ」とだけ出す（従来どおり）。
  - 数はカートの分を引かない値。案1〜3は在庫の残り、セットは「残りセット数」と「3絵柄の在庫で作れるセット数」の少ない方（レジ画面と同じ考え方）。セットにも絵柄と同じ基準を使う。
  - 表示データに `low_stock`（基準以下で1以上の商品とその残り数だけ。例 `{ design_3: 4, set: 2 }`）を足す。判定はレジ画面側で行う（`displayLowStock`）。古い版のレジからのデータには無いので、その場合は残り数を出さない。
  - レジ画面の表示（「残り◯」「残り◯セット」「残りわずか」）は変えない。
- ダッシュボード：タイル「セット 販売済み／上限」に「販売済み／上限」と残りセット数。**日付の切り替えに関係なく全期間**で数える（上限は全期間に対するものなので）。

**オフラインの端末が複数あるとき**
- 在庫（D-15）と同じく、オフライン中の端末には他の端末の販売が届かないため、それぞれが「まだ残りがある」と判断して、**上限をわずかに超えて売れることがある**。会計は止めない原則（オフラインでも会計入力を止めない）を優先し、超えた分も正しい会計として記録する（取消しない）。
- 超えた場合、全端末が同期した後の残りは 0 と表示される（マイナスにしない）。実際の販売数はダッシュボードの「販売済み」と CSV で分かる。
- 運用で補う：残りが少なくなったら、レジ同士で口頭で確認する（`docs/operations.md`）。

**セキュリティルール**
- `settings.set_limit` は 0〜100 の整数のときだけ保存できる。
- `set_limit` を変える書き込みは、同じ書き込みで**新しく作られる** `set_limit_change` の記録を指している場合だけ通す。既存の記録の使い回しは不可。上限を変えない保存（価格など）は記録なしで通る。
- `set_limit_change` の記録は、同じ書き込みで settings がその記録を指している場合だけ作れる。`is_test=true` にはできない。
- 記録の「変更前」の値はルールでは照合しない（上のオフラインの同時変更で、後から届いた方の書き込みが拒否され、上限の変更ごと失われるのを避けるため）。
- `display_state` の「書いてよい項目」に `low_stock` を足した（数だけで、個人情報ではない）。

**CSV・検査**
- `action_logs.csv` の `log_type` に値 `set_limit_change` が加わる（列は変えない。D-14）。`scripts/check_csv.py` はこの値を正しいコードとして扱い、`is_test=false`・`note` の形・値が 0〜100 であることを検査し、変更の履歴を表示する。

**本番に出す順番**：表示データに `low_stock` が増えるため、**ルールのデプロイ → アプリの公開** の順にする（D-29 と同じ理由。新しいルールは古いアプリの書き込みもそのまま受け付ける）。

## D-31 Tailwind CSS の導入（状態：確定 2026-10-30）

スタイルを Tailwind CSS で書く方針に変える（ユーザーの指示）。既存の画面（`src/styles.css`）を崩さずに導入する。

- 入れたもの：`tailwindcss` と `@tailwindcss/vite`（どちらも 4.3.3、開発用の依存）。設定ファイル（`tailwind.config.js`・PostCSS）は使わず、v4 の CSS での設定にする。
- 入口は `src/index.css`（`src/main.tsx` から読み込む）。`styles.css` は中身を変えずに、ここから読み込む。
- **層の順番**：`theme`（Tailwind の変数）＜ `base` ＜ `components`（既存の `styles.css` 全体）＜ `utilities`（Tailwind のクラス）。要素に Tailwind のクラスを足すと、既存のクラスより優先される。そのため、画面ごとに少しずつ Tailwind に置き換えていける（置き換えたら、使わなくなった `styles.css` の規則を消す）。
- **Tailwind のリセット（preflight）は読み込まない**。読み込むと、見出し・ボタン・入力欄・画像などの既定の見た目が変わり、既存の画面が崩れるため。基本の整え（`box-sizing`、`body` の余白、ボタン・入力欄の文字）は、これまでどおり `styles.css` の先頭で行う。
- **色**：`styles.css` の色の変数（D-26）を Tailwind の色として登録した（`@theme inline`）。例：`bg-surface`、`text-text-2`、`border-border`、`text-warn`、`bg-warn-soft`、`text-d1-ink`、`bg-confirm`。変数の値はライト／ダークで切り替わるので、これらのクラスは `dark:` を付けなくても両方の表示モードに対応する。Tailwind の既定の色（`red-500` など）も使えるが、表示モードに合わせるため、原則としてこれらの色を使う。
- **`dark:`**：アプリの表示モードの決まりに合わせた（端末がダーク かつ ライト指定でない、または `data-theme="dark"`。`src/lib/theme.ts`）。
- **クラス名の重なり**：既存のクラス `table`・`grow` は Tailwind にも同じ名前がある。既存の見た目を変えないよう、この2つ（と、テストの文字列から拾われる `sepia`）は Tailwind に作らせない（`@source not inline(...)`）。`styles.css` に Tailwind と同じ名前のクラスを足すときは、ここにも足す。
- クラスを探す範囲は `src` だけ（docs・scripts の文章からクラスが作られないように）。
- **確認したこと**：導入後のビルドで、`components` 層の中身が導入前の `styles.css` のビルドと一致すること（同じ方法で整形して比較）、Tailwind のクラスがまだ1つも出力されていないこと、層の外に規則が無いことを確かめた。つまり導入した時点では画面の見た目は変わらない。lint・typecheck・ユニット・E2E（Service Worker を含む）も合格。
- ボタンは縦横48px以上（要件）を Tailwind で書くときも守る（例：`min-h-12 min-w-12`）。
